### What this proves

- librime 1.17's vtable-only C API is usable from Swift: no legacy `RimeInitialize` free
  functions exist, and the `data_size` self-versioning idiom ports cleanly.
- YAML to prism/table/reverse deployment works with only `shared_data_dir`, `user_data_dir`,
  `prebuilt_data_dir` and `staging_dir` set, with no third-party data and no OpenCC.
- Preedit, candidate list, selection and commit behave the way the keyboard UI expects.

### Deviations from the design

- **Value type names.** The Swift value types are `RimeCandidateItem`, `RimeCompositionInfo`
  and `RimeStatusSnapshot`. The short names collide with the C structs `RimeCandidate`,
  `RimeComposition` and `RimeStatus` that the `Rime` module already exports.
- **No separate `RimeSession` type yet.** The actor owns the session id directly. A session
  facade waits until the keyboard needs more than one.
- **Swift 5 language mode** for the package (`.swiftLanguageMode(.v5)`), matching the Xcode
  targets. Swift 6 strict concurrency around raw C pointers buys nothing in the tracer.
- **`translator/enable_user_dict: false`** in the tracer schema: no leveldb, so the
  app/extension lock-contention risk (R5) stays closed until we deliberately open it.
- **The library links through `RimeDynamicStub`**, while the tests and the CLI link the real
  `RimeDynamic`. That is the same shape the app (embeds) and the extension (resolves through
  its runpath) will use.

### Build environment caveat

Both `xcodebuild` and `swift build` fail inside the harness's workspace-write sandbox: Xcode
and SwiftPM spawn their own `sandbox-exec` helpers (SwiftPM's manifest sandbox, Xcode's
`swift-plugin-server` for the `#Preview` macro). A nested `sandbox-exec` invocation exits 71 with
"sandbox_apply: Operation not permitted". SwiftPM also needs access to the compiler module caches. Builds
therefore run with an escalated sandbox. This is a property of the harness, not of the project:
the same commands work normally in Terminal and in Xcode.

## P2 — first device run: two real bugs, both fixed

The first device run typed one character and then the keyboard vanished, with iOS falling back to
the previous input method. The probe log said the engine was healthy
(`fullAccess=true root=appGroup`, 9.4 MB), so the extension process was dying. It was.

### Bug 1 — the extension crashed on the first key

Two crash reports pulled off the phone (`xcrun devicectl device copy from --domain-type
systemCrashLogs`) both end the same way:

```
CoreAutoLayout  -[NSLayoutConstraint _setActive:mutuallyExclusiveConstraints:]
ARKeyboard      CandidateBar.makeSeparator()
ARKeyboard      CandidateBar.setCandidates(_:highlighted:)
ARKeyboard      KeyboardViewController.apply(_:)
ARKeyboard      KeyboardViewController.process(_:)
```

`setCandidates` created a separator and activated
`separator.heightAnchor == stack.heightAnchor` **before** adding the separator to the stack.
The two views shared no ancestor, so CoreAutoLayout raised
`NSInternalInconsistencyException` and the extension aborted (SIGABRT). One key press is enough:
the second candidate is what triggers the separator. iOS then shows the previous keyboard, which
is exactly the reported symptom.

Fix: the candidate bar was rewritten without a scroll view, and the separator now lives inside its
own candidate's bounds, so every constraint is activated between views that already share a
superview. The rule is written down in the file so it does not come back.

### Bug 2 — the bottom row overflowed (found by the new preview)

The row places `123 | emoji | space | 辅码 | return`, with the space bar as the "remainder"
item. The remainder was computed as `usable - consumed`, where `consumed` only counted the
items placed *before* it. Because the space bar sits in the middle of the row, the two keys to its
right were pushed off the screen: 辅码 was clipped and 换行 was invisible.

Fix: the remainder subtracts every unit-sized item in the row, whatever its position.

### What changed so this cannot repeat

- `KeyboardUI/` (metrics, theme, key button, candidate bar, key grid) is now a synchronized
  folder compiled by **both** targets.
- The host app renders that same view hierarchy in a preview section on its main screen, so the
  keyboard's appearance and its layout code can be exercised from a simulator screenshot.
  The overflow bug above was invisible until the preview existed; it was found within a minute of
  the preview first rendering.
- The candidate bar is constraint-light by construction, and the layout rule is documented where
  it was broken.

## P2 follow-up — the input path was the problem

The second device run typed but felt laggy and often produced nothing. The probe log cleared the
engine of suspicion: boot takes 1.7–4.7 ms and the process sits at 6–9 MB. The input path was at
fault, in three separate ways.

### 1. Every key hopped through an actor

`send(_:)` wrapped each keystroke in `Task { await engine.processKey(...) }`: two scheduling
hops per key, and the order of concurrent keys left to the scheduler. `RimeEngine` is no longer
an actor. It is a plain class owning a dedicated serial queue, and every public method runs its
body on that queue, so callers get an ordinary synchronous call with no hops and strict ordering.
The keyboard calls it directly from the main thread, where a key press is well under a
millisecond.

### 2. Every key rebuilt the whole interface

- `CandidateBar.setCandidates` destroyed and recreated all five buttons, their separators and
  their constraints on each keystroke. It now pools the buttons and only updates titles,
  visibility and the highlight.
- `KeyboardKeyGrid.configure` restyled roughly 45 views (fonts, colours, and `UIImage(systemName:)`
  lookups for shift/delete/emoji/globe) on every key. It now compares against the last applied
  configuration and returns immediately when nothing changed.
- `textDidChange` — which fires on every marked-text update — restyled the grid too. It now does
  work only when the keyboard appearance actually changed.

A stalled main thread is also how UIKit silently drops touches, so this was a plausible
contributor to keys that never appeared.

### 3. Keys librime declined vanished

The tracer schema has no `punctuator`, so librime refuses `.` and `,` outright: `handled`
comes back false with no commit. The controller did nothing in that case, so the key produced
nothing at all. It now types the literal character whenever librime declines the key and there is
no active composition — the same contract native keyboards have with their input engine. A
regression test (`testSchemaDeclinesPunctuation`) pins the precondition that made this visible.

### New evidence: per-key latency

The controller now measures the key path (engine call plus UI update) and appends a
`keyboard.stats` record to the probe log every 25 keys, plus a flush when the keyboard
disappears. Keys slower than 50 ms are logged individually to the system log. That turns "feels
laggy" into `keys=25 avgMs=… maxMs=…` in the diagnostics screen.


## P3 — launch budget on device: measured

Same app, same phone, two builds, neither started from Xcode:

| | Debug build, started from Xcode | Release build, started via devicectl |
| --- | --- | --- |
| process start to App.init (dyld) | 16556 ms as reported | **10–16 ms** |
| App.init to first appearance | 12309 ms as reported | **66–81 ms** |
| engine check, now on a background task | 54 ms | **28–35 ms** |

The Release column is the real launch: the app is usable roughly **100 ms** after it starts, and
loading librime's 4.9 MB framework costs 10–16 ms. The app bundle is 6.1 MB, of which the framework
is 4.9 MB.

The Debug column is not a launch measurement, which is why it needs spelling out: iOS had
**prewarmed** the process long before the icon was tapped, so "time since process start" includes
the waiting, not the starting; the app then sat suspended between init and first appearance; and
Xcode holds a Debug build at main until the debugger attaches. On top of that the Debug
configuration carries `-Onone`, a debug dylib and the SwiftUI previews dylib.

Consequence for the rest of the work: judge launch and typing feel on a Release build started from
the home screen. A Cmd-R run in Xcode measures Xcode.

### How the numbers are collected

`arkeyApp.init()` and `ContentView.onAppear` mark a timeline; the engine check runs on a
background task so it never sits between the user and the first frame; and the marks are written to
the probe log as an `app.launch` record. The kernel's process start time is read with
`sysctl(KERN_PROC_PID)`, which is what separates dyld from our own code — and which is worth a
unit test, because the first version of it subtracted a wall-clock timestamp from seconds-since-boot
and a later one underflowed a UInt64 by reading the clock before touching the static it was
initialised from. Both were caught and fixed, the second by the crash report.

The log lives in the app group container, which `devicectl` refuses to copy (it rejects any path
with a spurious "File paths cannot contain '..'"). The app mirrors it into its own Documents
directory on every launch, and that container copies fine, so the log can be pulled over USB
without anyone copying text by hand.

### Still open

- The keyboard extension's own launch cost: its boot record now carries `ageMs`, the time from the
  extension process starting to its engine being ready. That is the number that decides how fast
  the keyboard appears, and it needs one run on the device.
- Typing feel on a Release build, with the `keyboard.stats` records from the same session.
- Pagination, the emoji layer, and a real behaviour for the aux-code key are still out of scope.
- The punctuation gap is a schema decision, not a code one: the tracer schema needs a
  `punctuator` section (or an imported preset) before it can produce Chinese punctuation.
